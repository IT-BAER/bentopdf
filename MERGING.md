# Merging from Upstream Without Losing Fork Changes

This is a **fork** of [`alam00000/bentopdf`](https://github.com/alam00000/bentopdf).
It carries a set of customizations that upstream does **not** have. Upstream
merges routinely touch the same files, so a careless `git merge upstream/main`
will silently drop fork features. This document is the safety net: it lists
what is fork-owned, gives a repeatable merge procedure, and a checklist to
verify nothing was lost.

## Remotes

```
origin     https://github.com/IT-BAER/bentopdf.git   (this fork)
upstream   https://github.com/alam00000/bentopdf.git (original)
```

If `upstream` is missing:

```powershell
git remote add upstream https://github.com/alam00000/bentopdf.git
```

take `--theirs` or `--ours` — read both sides and fold upstream's change into
the fork logic.

### Generated / artifacts — DO NOT hand-merge, regenerate or ignore

Conflicts in these are noise. Take either side, then rebuild:

- `public/sitemap.xml` — regenerated by `scripts/generate-sitemap.mjs` during `npm run build`
- i18n tool pages — regenerated by `scripts/generate-i18n-pages.mjs` during `npm run build`
- `docs/.vitepress/cache/**` — VitePress cache (should be gitignored)
- `verify-output.txt`, `dist-1.9.3.zip` — stray build artifacts (should not be tracked)

> Regenerate the live fork-owned list any time:
>
> ```powershell
> git fetch upstream
> git diff --name-only upstream/main...main
> ```

## Merge procedure (PowerShell)

```powershell
# 0. Clean tree on an up-to-date main
git switch main
git status            # must be clean
git pull origin main

# 1. Safety backup branch (dated)
$today = Get-Date -Format 'yyyy-MM-dd'
git branch "backup-before-upstream-merge-$today"

# 2. Fetch upstream and preview what is coming
git fetch upstream
git log main..upstream/main --oneline      # new upstream commits
git diff --stat main upstream/main         # files that will change

# 3. Merge (use a release tag if you prefer: upstream/<tag>)
git merge upstream/main

# 4. Resolve conflicts
#    - Fork-owned file (see list above): keep fork logic, fold in upstream change.
#    - Generated/artifact file: take either side, it gets rebuilt in step 5.
git status                                  # see conflicted files

# 5. Reinstall + rebuild (regenerates sitemap + i18n pages)
npm ci
npm run build

# 6. Verify
npm run test:run
npm run lint

# 7. Finish
git commit            # completes the merge (keep a descriptive message)
git push origin main
```

If a merge goes wrong, abort and start over — nothing is lost:

```powershell
git merge --abort
# or, if already committed:
git reset --hard "backup-before-upstream-merge-$today"
```

## Post-merge verification checklist

Run the app (`npm run dev`) and confirm the fork features still work:

- [ ] **Simple mode** — with `public/config.js` `simpleMode: true`, header + hero + footer are hidden; with `false`, full layout shows.
- [ ] **Theme** — dark/light toggle and accent-color picker work from the navbar.
- [ ] **Language** — language switcher works; German strings load; localized routes resolve.
- [ ] **Rotate PDF** — load multiple PDFs, rotate, apply. On Chromium the **Save As dialog opens defaulting to the source file's folder with the same filename** (not auto-download to Downloads).
- [ ] **Save dialog (other tools)** — `downloadFile` still opens a Save As dialog instead of silent download.
- [ ] **Build** — `npm run build` regenerates `public/sitemap.xml` and the i18n tool pages.
- [ ] **CI** — `.github/workflows/*` still scoped to this fork (no upstream-only jobs reintroduced).
- [ ] **Tests + lint** — `npm run test:run` and `npm run lint` pass.

## Why no automatic merge driver?

A `.gitattributes` `merge=ours` rule was considered but rejected for now: most
fork-owned files (`helpers.ts`, `rotate-pdf-page.ts`, `main.ts`, locales) are
files upstream **also** edits, so auto-keeping our copy would silently discard
genuine upstream improvements (bug fixes, new tools). The documented procedure +
verification checklist above is the deliberate trade-off: a human folds the two
sides together. Revisit only if a file becomes truly fork-exclusive (upstream
never touches it).
